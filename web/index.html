How the system works

Report §§4-5 · pp.5-6
Device simulatorBrowser client or device.py. Holds the matching sample key and computes an HMAC.
↔
HTTP(S) JSON interface POST /challenge
POST /authenticate
Keys omitted from authentication POSTs.
↔
Authentication server server.py reads the JSON registry and holds pending sessions in process-local memory.
  1. Identify: the device requests a challenge with its registered device_id. Unknown IDs are refused.
  2. Challenge: secrets.token_bytes(32) generates 32 random bytes (256 bits); secrets.token_urlsafe(18) generates the session ID. Both are bound to a device ID and a monotonic expiry time.
  3. Compute: the device uses its assigned symmetric key to compute HMAC-SHA-256 over the complete session context.
  4. Submit: send device_id, session_id, and the 64-character hexadecimal proof to /authenticate.
  5. Consume and verify: a lock protects challenges.pop(session_id, None). For a well-formed authentication attempt, removal happens before identity, expiry, and proof checks. The server recomputes the HMAC and uses hmac.compare_digest on the fixed-length hex proofs.

The exact authenticated message

message = b"INS-IOT-AUTH-v1" + b"|" + device_id.encode("utf-8")
          + b"|" + session_id.encode("ascii") + b"|" + challenge_bytes
proof   = HMAC-SHA-256(device_key, message).hex()

The fixed domain label separates this use of a key from other protocols. The challenge is decoded from Base64URL into raw bytes before HMAC computation; the encoded challenge text is not the input. HMAC is a symmetric message authentication code, neither encryption nor a public-key digital signature.

Why these choices matter

A server-selected challenge avoids a reusable static response. Device and session IDs bind the proof to a particular claimant and exchange. Atomic consumption permits at most one verification attempt per session, even for an invalid proof. Expiry bounds how long an unused challenge can authenticate.

Constant-time comparison is a source-level implementation property; browser round-trip timings cannot prove it. Malformed requests rejected with HTTP 400 before verification do not consume a session. Expired sessions become unusable; this prototype does not proactively purge abandoned records from memory.

Security properties and their limits

Report §§3, 6 · pp.5, 7

Threat model: an attacker may observe, modify, delay, or replay messages. The design assumes strong private per-device keys that cannot be extracted from devices or the server. Public classroom fixtures do not satisfy that assumption.

What each property establishes
Property / threat Mechanism and evidence Boundary
Device authentication / impersonation Registered ID and keyed proof; ST-1, ST-2, device-binding probe. A copied key enables impersonation. Authentication does not authorize individual commands.
Proof integrity / tampering HMAC covers label, ID, session, and challenge; ST-3 and context probes. No encryption of readings or metadata; no telemetry or command endpoint is implemented.
Freshness / delayed requests Secure random challenge and 60-second TTL; freshness probe and ST-5. Different observed values do not prove unpredictability. Random generation relies on Python's secrets module.
Replay resistance Atomic removal before proof checking; ST-3 and ST-4. Restart invalidates pending sessions. Multiple processes do not share state; clustered operation needs shared atomic state.
Transport confidentiality / eavesdropping Optional Python TLS socket; transport observation and ST-7 procedure. HMAC supplies no channel confidentiality. HTTP stays on localhost; deployment needs verified TLS.
Input handling Type, length, and JSON shape checks with 400/401 responses; ST-6. Generic rejection does not supply rate limiting, denial-of-service resistance, or a production audit.

Key management and operation

The registry is unencrypted JSON with distinct, public demo keys. Real devices need unique high-entropy keys, authenticated provisioning, secure elements or equivalent storage, revocation, replacement, rotation, audit procedures, and secure backups.

Production also needs request limits, monitoring, authorization, and durable atomic replay state. Console request logs are not an audited monitoring system. HMAC alone does not provide these controls.

Applications and future work

Relevant to smart-home sensors, environmental monitoring, industrial telemetry, and classroom gateway testbeds. This is simulated identity establishment, not a physical IoT deployment.

Future work, not implemented: mutual authentication, certificate-based device identity, secure enrollment, command authorization, protected hardware keys, rotation, revocation lists, clustered replay state, and MQTT over verified TLS. There is no production database or certificate issuance service.

Requirements and project structure

A computer with Python 3.10+ and a modern browser. Server and CLI simulator use only Python's standard library. The browser uses built-in Web Crypto on HTTPS or trustworthy loopback origins. Git is optional when you already have the files.

iot-auth-project/
  server.py              challenge service and verifier
  device.py              command-line device simulator
  data/demo_devices.json public classroom registry
  web/index.html         dashboard and browser simulator
  verify_tls.py          ST-7 validating CLI check
  README.md              setup and limitations
  report/                CCA PDF, source, and emblem
  tests/                 regression checks

A real target additionally needs networking, sound cryptographic facilities, and protected persistent storage for a unique device key.

ST-7 · Configure TLS and validate certificates

Transport has not been checked yet.

  1. Provide a trusted local certificate cert.pem and matching private key key.pem. Its Subject Alternative Name must match the hostname or IP used by the client. Do not commit private keys.
  2. Start a TLS listener:
    python server.py --host 127.0.0.1 --port 8443 --tls-cert cert.pem --tls-key key.pem
  3. Open https://127.0.0.1:8443/ in a client that trusts the issuing CA. Inspect the certificate and authenticate. Do not bypass certificate warnings.
  4. For a repeatable CLI check, use the issuing CA and a separate unrelated CA file. The verifier checks hostname, expiry, trust, and successful authentication, then confirms rejection with the unrelated CA. Trust is restricted to the test client; OS trust is unchanged.
    python verify_tls.py --server https://127.0.0.1:8443 --ca-file local-ca.pem --untrusted-ca-file unrelated-ca.pem --output tls-evidence.json
  5. ST-7 is complete only when both trusted authentication and untrusted-certificate rejection pass. Keep the verifier's JSON output with your downloaded dashboard evidence. This page never infers a PASS from the URL.

TLS support does not guarantee a particular negotiated version. Server metadata shows the version negotiated for that request. Certificate issuance, trust distribution, and mutual TLS remain outside this prototype.

Imported evidence is labelled as an external CLI observation, not a browser-generated test or independent attestation.
